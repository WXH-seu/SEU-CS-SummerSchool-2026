## 第四周角色调整：子系统管理员作用域与三元归一化（进行中）

为了让“子系统管理员 = 部分子系统的管理员”而不是一个全局管理员，并让业务子系统（成员 D/E 采用 管理员/教师/学生 三元）对我们这套“四元 + 作用域”透明，做了如下改动：

- [x] 新增 `SubSystem` 枚举（学籍/选课/图书馆/商店）+ `SubSystems` 工具；`LoginResponse / AccountInfo / RegisterRequest` 携带 `adminScopes`（被授权子系统 key 集合）。
- [x] 数据库：`tblUser` 增加 `adminScopes` 列（旧库自动 `ALTER TABLE` 迁移）；种子 `admin` 授予全部四个子系统。
- [x] 权限：`PermissionPolicy.allows(op, role, scopes)` 先按 `effectiveRole` 归一化——**授权子系统内为管理员，未授权子系统归一化为教师（保留使用权限、无管理权）**；“管理/维护类”操作仅管理员（`SUBSYSADMIN/SUPER_ADMIN`），“使用类”操作对普通用户与管理员开放。
- [x] 透明度：新增 `SubSystemRole`（`ADMIN/TEACHER/STUDENT`）与 `SubSystems.effectiveRole(role, scopes, subSystem)`，把“四元 + 作用域”归一化为针对某一子系统的三元角色，供子系统直接取用（队友无需改三元体系）。
- [x] 注册：`RegisterFrame` 角色选“子系统管理员”时出现**可管理子系统复选框（至少一个）**；`AuthService` 校验作用域非空；CSV 仅导入学生/教师（管理员角色拒绝）。
- [x] 客户端：`MainFrame` 子系统管理员可进入全部子系统；`AccountFrame` 用户表与“我的账号”显示“权限范围”。
- [x] 测试：新增作用域归一化、作用域外使用/管理行为、`SubSystemRole` 映射、`adminScopes` 序列化；全量通过（见测试记录）。

> 开发协作约定：业务子系统的请求只要调用 `SubSystems.effectiveRole(role, scopes, subSystem)` 拿到各自子系统的 `SubSystemRole`，即可按“管理员/教师/学生”三元逻辑处理，无需关心内部四元分级与作用域。
