## 2. 技术实现说明

### 2.1 面向对象分层

- 公共层使用 DTO 与 `Operation` 表达跨网络的数据和行为契约。
- 客户端由 `AcademicManagementPanel` 负责交互，`AcademicClientService` 负责请求封装。
- 服务端由请求处理器分派操作，`AcademicService` 与 `CurriculumCatalogService`
  分别封装可写学籍规则和只读目录规则。
- DAO 只处理 Access 表结构与 SQL，界面不直接连接数据库。
- 依赖通过构造方法注入，使服务可在临时数据库中独立测试。

### 2.2 角色与权限

学籍模块只接收当前子系统的 `STUDENT / TEACHER / ADMIN` 有效角色，不判断全局角色。
学生查询学籍时，服务端通过登录账号反查本人记录，忽略客户端提交的其他筛选条件；
公开的专业和培养方案目录允许所有已登录角色只读查询。

### 2.3 数据一致性

- 应用层在删除前查询引用并返回明确的 `CONFLICT`，避免把底层 SQL 异常直接暴露给用户。
- 数据库层保留主键、外键、唯一性和非空约束，作为第二层保护。
- 商店旧表通过元数据检查后执行 `ALTER TABLE` 补充用户外键，不删除已有合法数据。
- 删除学生或教师前，根据其 `userId` 检查图书馆、购物车和订单记录，避免删除学籍后业务记录失去身份映射。
- 选课旧结构升级时按外键依赖顺序先删除选课、受众、时段和修读记录，再重建课程与教学班。
- 最终数据库验证在临时副本完成，没有覆盖本机正在使用的 `vCampus.accdb`。

### 2.4 公开目录与实际开课分离

`tblCatalogCourse` 保存官网培养方案中的课程定义和来源；`tblCourse` 保存当前实际开课的
教师、时间、地点、容量与开放状态。客户端目录只读，避免把公开课程样例误当成可选教学班。
