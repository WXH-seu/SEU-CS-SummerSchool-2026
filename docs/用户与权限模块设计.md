# 用户与权限模块设计

> 负责人：阴立暄（成员 A） · 分支：`feature/yin-user-auth`
> 状态：已完成注册、登录、登出、注销、账号管理与角色授权（含超级管理员分级），通过单元与端到端测试。

## 1. 模块目标

- 支持学生、教师、管理员与超级管理员四类角色的登录、登出与注销；账号由管理员统一创建。
- 服务端统一完成身份认证与基于角色的权限检查，未登录返回 `UNAUTHORIZED`，权限不足返回 `FORBIDDEN`。
- 密码使用 PBKDF2 加盐哈希保存，任何日志、界面和数据库字段均不出现明文密码。
- 用户模块在 Swing 客户端、Socket 服务端与 Access 数据库之间形成完整闭环。

## 2. 数据库设计

Access 表 `tblUser`（由服务端首次启动时通过 UCanAccess 自动创建）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `userId` | TEXT(32) | 账号，主键 |
| `passwordHash` | TEXT(128) | PBKDF2 哈希值（Base64），不保存明文 |
| `passwordSalt` | TEXT(64) | 随机盐（Base64） |
| `displayName` | TEXT(64) | 显示名 |
| `roleName` | TEXT(16) | 角色：`STUDENT` / `TEACHER` / `SUBSYSADMIN` / `SUPER_ADMIN` |
| `adminScopes` | TEXT(64) | 子系统管理员可管理的子系统 key（逗号分隔，如 `student,course`）；其他角色为空 |
| `active` | YESNO | 是否启用，管理员可禁用账号 |

审计日志表 `tblOperationLog`（记录登录与管理员操作，便于回溯追责）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `logId` | COUNTER（自增主键） | 日志编号 |
| `logTime` | DATETIME | 记录时间 |
| `userId` | TEXT(32) | 操作者 / 尝试登录的账号 |
| `operation` | TEXT(32) | `LOGIN` / `LOGIN_FAILED` / `REGISTER` / `IMPORT_CSV` / `UPDATE_STATUS` / `DELETE` |
| `targetUserId` | TEXT(32) | 目标账号（可空） |
| `detail` | TEXT(255) | 说明 / 失败原因 |
| `success` | YESNO | 是否成功 |

演示账号（种子数据，首次建库时写入）：

| 账号 | 密码 | 角色 |
| --- | --- | --- |
| `superadmin` | `super123` | 超级管理员 |
| `admin` | `admin123` | 子系统管理员（可管理全部子系统：学籍/选课/图书馆/商店） |
| `student` | `student123` | 学生 |
| `teacher` | `teacher123` | 教师 |

安全规则：

- 客户端不直接连接 Access，数据库文件只由服务端访问。
- 所有 SQL 使用 `PreparedStatement`，不拼接用户输入。
- 密码最小长度为 6 位，由服务端统一校验。

## 3. 权限矩阵

权限定义在 `vcampus-server` 的 `PermissionPolicy` 中，是全部模块统一的权限检查入口。

| 操作 | 学生 | 教师 | 子系统管理员 | 超级管理员 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `PING` | ✓ | ✓ | ✓ | ✓ | 公开，无需登录 |
| `USER_LOGIN` | ✓ | ✓ | ✓ | ✓ | 公开 |
| `USER_REGISTER` | — | — | — | ✓ | 仅超管注册用户 |
| `USER_IMPORT_CSV` | — | — | — | ✓ | 仅超管 CSV 批量导入 |
| `USER_LOGOUT` | ✓ | ✓ | ✓ | ✓ | 登录用户 |
| `USER_ACCOUNT_QUERY` | ✓ | ✓ | ✓ | ✓ | 查询自己的账号 |
| `USER_PROFILE_UPDATE` | ✓ | ✓ | ✓ | ✓ | 修改显示名 |
| `USER_PASSWORD_CHANGE` | ✓ | ✓ | ✓ | ✓ | 修改密码 |
| `USER_DELETE` | ✓ | ✓ | ✓ | ✓ | 注销自己的账号 |
| `USER_LIST_QUERY` | — | — | — | ✓ | 仅超管列出全部用户 |
| `USER_STATUS_UPDATE` | — | — | — | ✓ | 仅超管启用/禁用账号 |
| `USER_AUDIT_QUERY` | — | — | — | ✓ | 仅超管查看登录/操作日志 |
| `STUDENT_QUERY` | ✓ | ✓ | ✓ | ✓ | 学生仅返回本人学籍；教师/管理员按条件查询 |
| `STUDENT_SAVE` | — | — | ✓ | ✓ | 学籍·维护（仅管理员） |
| `COURSE_QUERY` | ✓ | ✓ | ✓ | ✓ | 选课模块默认值 |
| `COURSE_SELECT` / `COURSE_DROP` | ✓ | — | — | ✓ | 选课模块默认值 |
| `LIBRARY_BOOK_QUERY` | ✓ | ✓ | ✓ | ✓ | 图书馆·查询 |
| `LIBRARY_BOOK_SAVE` / `LIBRARY_BOOK_DELETE` | — | — | ✓ | ✓ | 图书馆·维护（仅管理员） |
| `LIBRARY_BORROW` / `LIBRARY_RETURN` | ✓ | ✓ | ✓ | ✓ | 图书馆模块默认值 |
| `STORE_PRODUCT_QUERY` | ✓ | ✓ | ✓ | ✓ | 商店模块默认值 |
| `STORE_ORDER_CREATE` | ✓ | ✓ | ✓ | ✓ | 商店模块默认值 |

> 上表仍是**占位矩阵**，供各业务模块集成时调整。三列用户（学生/教师/子系统管理员）的划分原则：**“管理/维护类”操作（如 `*_SAVE`）仅管理员（子系统管理员/超级管理员）**；**“使用类”操作（查询/选课/借还/下单）对普通用户（学生/教师）与管理员开放**。

> 各业务模块负责人通过 `policy.requireSubSystem(operation, SubSystemRole...)` 调整业务权限，无参调用表示“任意已登录的有效角色”；全局 `Role` 只用于用户与账号模块。
> 超级管理员作为全局管理员拥有业务模块的最大访问权限，成员可按需放宽或收紧。
>
> **子系统管理员的“作用域”规则**：`SUBSYSADMIN` 在其**被授权**的子系统里是管理员（可做 `*_SAVE` 等管理操作）；在**未被授权**的子系统里会被归一化为**教师**——保留普通使用权限（查询/选课/借还/下单，与学生/教师同等），但不具备管理权（`*_SAVE` 等管理操作仍返回 `FORBIDDEN`）。因此它**不会**被锁在子系统之外，只是不能在未授权子系统里做管理。`SUPER_ADMIN / TEACHER / STUDENT` 不受作用域限制。

### 3.1 注册策略与管理员分级

账号创建是**管理员专属**操作，不开放自助注册。系统区分两层管理员：

| 角色 | 定位 | 权限 |
| --- | --- | --- |
| `SUBSYSADMIN` | 子系统管理员（如学籍系统管理、图书馆子系统管理） | **仅操作其被授权的若干业务子系统**；不能注册用户、不能管理账号 |
| `SUPER_ADMIN` | 全局超级管理员 | 注册用户（任意角色）、CSV 批量导入、列出/启用/禁用账号、查看操作日志 |

注册规则：

- 学生、教师、子系统管理员（`SUBSYSADMIN`）、超级管理员（`SUPER_ADMIN`）：一律由**超级管理员**注册（单个注册 `USER_REGISTER` 或 CSV 批量导入 `USER_IMPORT_CSV`）。
- **子系统管理员登记时需要勾选它可管理的子系统**（至少一个）：注册界面用复选框列出全部四类子系统（学籍管理 / 选课系统 / 图书馆 / 校园商店），勾选结果写入账户的 `adminScopes`。
- 若以 `SUBSYSADMIN` 角色注册但未勾选任何子系统，服务端返回 `INVALID_REQUEST`（“子系统管理员至少需要勾选一个子系统”）。
- **CSV 批量导入仅支持学生/教师**，出现管理员角色（`SUBSYSADMIN / SUPER_ADMIN` 或中文“管理员/子系统管理员/超级管理员”）会被拒绝——管理员必须在界面手动注册并勾选子系统权限。
- 子系统管理员（`SUBSYSADMIN`）**不再具备账号管理权限**，只负责其所辖业务子系统的日常操作。

登录界面**不提供注册入口**，只提示“账号由管理员创建，如需新账号请联系管理员”。

服务端在两层都做校验：

1. `RequestDispatcher` 按权限矩阵拦截：非超管访问 `USER_REGISTER / USER_IMPORT_CSV / USER_LIST_QUERY / USER_STATUS_UPDATE / USER_AUDIT_QUERY` → `FORBIDDEN`；`SUBSYSADMIN` 越出其 `adminScopes` 时按 `TEACHER` 使用业务模块，但管理操作返回 `FORBIDDEN`。
2. `AuthService` 做二次校验（`requireSuperAdmin`，仅超管）；账号创建与状态变更再结合目标角色门控，防止绕过 dispatcher 越权。

### 3.2 对子系统透明：归一化的“三元有效角色”

我们这套是**四元角色 + 作用域**（`SUPER_ADMIN / SUBSYSADMIN / TEACHER / STUDENT` + `adminScopes`），而负责业务子系统的同学使用的是**管理员/教师/学生三元**用户体系。为避免让子系统改动它们的用户模型，我们在**本模块的边界上做归一化**，只向子系统输出一个“针对某个子系统的三元角色” `SubSystemRole`（`ADMIN / TEACHER / STUDENT`）。这样四元分类与作用域对子系统**完全透明**。

映射关系（针对某个具体子系统）：

| 会话角色 | 该子系统是否在 `adminScopes` 内 | 暴露给该子系统的 `SubSystemRole` |
| --- | --- | --- |
| `SUPER_ADMIN` | — | `ADMIN` |
| `SUBSYSADMIN` | ✓ | `ADMIN` |
| `SUBSYSADMIN` | ✗ | `TEACHER`（仅使用权限） |
| `TEACHER` | — | `TEACHER` |
| `STUDENT` | — | `STUDENT` |

- 该映射由 `vcampus-common` 的 `SubSystems.effectiveRole(role, scopes, subSystem)` 计算，服务端 `PermissionPolicy` 也直接使用 `SubSystemRole` 描述业务权限。
- `RequestDispatcher` 是服务端转换边界；子系统处理器和服务只接收登录 `userId` 与 `SubSystemRole`，无需知道内部有无 `SUBSYSADMIN`、`adminScopes`。
- 效果：一个只被授权“图书馆”的子系统管理员，在图书馆显示为 `ADMIN`（能管理），在学籍/选课/商店显示为 `TEACHER`（能用、不能管理）。

## 4. 通信协议

### 4.1 操作类型（`Operation`）

用户模块操作：

- `USER_REGISTER` — 管理员注册单个用户（学生 / 教师 / 管理员）
- `USER_IMPORT_CSV` — 管理员 CSV 批量导入（主要面向学生）
- `USER_ACCOUNT_QUERY` — 查询当前账号信息
- `USER_PROFILE_UPDATE` — 修改显示名
- `USER_PASSWORD_CHANGE` — 修改密码
- `USER_DELETE` — 注销（删除）账号
- `USER_LIST_QUERY` — 管理员查询用户列表
- `USER_STATUS_UPDATE` — 管理员启用/禁用账号

### 4.2 请求体（`vcampus-common` DTO）

| 操作 | 请求体 | 响应体 |
| --- | --- | --- |
| `USER_LOGIN` | `LoginRequest` | `LoginResponse` |
| `USER_REGISTER` | `RegisterRequest` | `AccountInfo`（被创建账号） |
| `USER_IMPORT_CSV` | `UserImportRequest` | `UserImportResponse`（成功数 + 失败明细） |
| `USER_ACCOUNT_QUERY` | 无 | `AccountInfo` |
| `USER_PROFILE_UPDATE` | `ProfileUpdateRequest` | `AccountInfo` |
| `USER_PASSWORD_CHANGE` | `PasswordChangeRequest` | 无 |
| `USER_DELETE` | `DeleteAccountRequest` | 无 |
| `USER_LIST_QUERY` | 无 | `UserListResponse` |
| `USER_STATUS_UPDATE` | `UserStatusUpdateRequest` | 无 |

#### CSV 批量导入格式

每行 `账号,密码,显示名[,角色]`，第 4 列可选，缺省为 `STUDENT`。角色仅可填
`STUDENT/TEACHER` 或中文 `学生/教师`，**管理员角色不支持 CSV 导入**（含旧别名 `ADMIN`/`管理员`、`SUBSYSADMIN`/`子系统管理员`、`SUPER_ADMIN`/`超级管理员`），出现即拒绝。空行、`#` 注释行与可选表头（首列含“账号”/“userId”）会被忽略。参考：

```text
账号,密码,显示名,角色
s001,secret123,学生一,STUDENT
s002,secret123,学生二,
```

### 4.3 响应码（`ResponseCode`）

- `SUCCESS` 成功；`INVALID_REQUEST` 参数错误；`UNAUTHORIZED` 未登录或凭据错误；
- `FORBIDDEN` 已登录但角色无权；`NOT_FOUND` 目标不存在；`CONFLICT` 账号已存在；
- `NOT_IMPLEMENTED` 接口预留；`SERVER_ERROR` 服务器内部错误。

## 5. 服务端结构

| 类 | 职责 |
| --- | --- |
| `server.security.PasswordHasher` | PBKDF2 加盐哈希与校验（Java 8 API） |
| `server.security.PermissionPolicy` | 权限矩阵与统一权限检查 |
| `server.session.SessionRegistry` | 线程安全的内存会话表，支持按用户批量失效 |
| `server.dao.UserRepository` / `AccessUserRepository` | 用户持久化（JDBC + UCanAccess） |
| `server.dao.OperationLogRepository` / `AccessOperationLogRepository` | 审计日志持久化（表 `tblOperationLog`） |
| `server.service.AuthService` | 登录、登出、注销、改密、资料与超管专属的账号管理业务 |
| `server.service.AuditService` | 记录登录与管理员操作（best-effort，不阻塞业务） |
| `server.service.AuthException` | 可预期的业务失败（携带响应码） |
| `server.dispatcher.RequestDispatcher` | 会话校验 → 权限校验 → 业务分发 → 统一异常处理 |

请求处理顺序（所有模块统一）：

```text
public 操作（PING/登录）→ 直接处理
其他操作 → 会话校验（失败返回 UNAUTHORIZED "请先登录"）
        → 角色校验（失败返回 FORBIDDEN "您没有权限执行该操作"）
        → 业务分发（管理员方法内部再做目标角色门控）→ 统一异常处理
```

## 6. 客户端界面

| 界面 | 功能 |
| --- | --- |
| `LoginFrame` | 登录；列出四个演示账号；不提供注册入口（提示账号由管理员创建） |
| `RegisterFrame` | 注册单个用户（超级管理员）（账号、显示名、初始密码、角色下拉含“超级管理员”）；角色选“子系统管理员”时出现**可管理子系统复选框（至少勾选一个）**，勾选结果写入 `adminScopes`；不给新用户建会话 |
| `MainFrame` | 主界面导航；顶栏显示身份、账号管理、退出登录；四个业务页面只接收当前子系统有效角色；**子系统管理员可进入全部子系统**（在未授权子系统仅有使用权限） |
| `AccountFrame` | 我的账号（查询/刷新，含权限范围）、修改资料（显示名、密码）、注销账号；**超级管理员**额外拥有“用户管理”页（列表、注册用户、批量导入CSV、启用/禁用，用户列表含“权限范围”列）与“操作日志”页 |

权限提示：

- 学生可进入“学籍管理”，服务端始终根据登录 `userId` 仅返回本人学籍，不能查询或修改他人资料。
- 服务端对越权请求返回 `FORBIDDEN`，客户端弹出“您没有权限执行该操作”。
- 未登录请求返回 `UNAUTHORIZED`，提示“请先登录”。
- 子系统管理员尝试注册或管理账号时，服务端返回“仅超级管理员可以创建管理员账号”。

## 8. 其他模块接入方式（供成员 D、E 参考）

1. 服务端：在 `RequestDispatcher` 中注册新操作的 `case`，调用对应 Service。
2. 权限：默认矩阵已为各模块预留，如需调整调用 `permissionPolicy.require(Operation, Role...)`；系统已内置“管理/维护类仅管理员、使用类对普通用户开放 + 子系统管理员作用域归一化”。
3. 取用当前用户在**你这个子系统**里的角色：调用 `SubSystems.effectiveRole(session.getRole(), session.getAdminScopes(), <你的子系统>)`，返回 `SubSystemRole`（`ADMIN`/`TEACHER`/`STUDENT`），据此按“管理员/教师/学生”三元逻辑处理即可，无需关心内部四元分级与作用域。
4. 客户端：新操作通过 `ClientConnection.request(...)` 发送，界面网络调用放在 `SwingWorker` 中。
5. 不要在日志中输出密码、完整会话令牌或敏感个人信息。
